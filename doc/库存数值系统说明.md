# 库存数值系统说明

> 适用模块：`warehouse/inventory/`、`warehouse/stock/`（统一库存变动服务、库存流水、历史库存、库存分析，第九–十三节）
> 关联模型：`Inventory`、`GoodsLocation`、`InventoryLotStock`、`StockLedger`、`StockDailyBalance`、`InventoryMetricsDaily`
>
> 实物库存（库位库存、待上架、已拣、已打包、已发未签）只能经 StockService 改，每次变动都写库存流水；`Inventory` 上的实物字段是行表的缓存（第九节）。

本文档说明库存页面所有数值字段的含义、计算方式，以及入库/出库各操作环节对这些数值的影响。阅读前需了解：系统中的库存数值分为两类——**实物位置类**（反映货物在哪个货位）和**流程过渡类**（反映货物正处于哪个业务环节）。

---

## 一、字段说明

### 1. 实物位置类（由 GoodsLocation 同步）

这三个字段的数据来源是 `GoodsLocation` 表（按库位类型合计），由 StockService 在每次库位库存变动时增量维护（第九节），对账核对两边一致。

| 字段 | 含义 |
|------|------|
| `onhand_stock` | 已上架到**标准货位**的实物数量，是日常库存管理的核心字段 |
| `damage_stock` | 已上架到**残次品货位**（damaged）的实物数量。**不能拣货出库**：拣货只能从 standard 库位拣（16162） |
| `return_stock` | 已上架到**退货货位**（return）的实物数量。同样不能拣货出库，要出库先移库到 standard 库位 |

### 2. 入库流程过渡类（ASN）

这三个字段随 ASN 入库流程流转，货物完成上架后归零。

| 字段 | 含义 |
|------|------|
| `asn_stock` | 供应商已生成 ASN、**货物尚未到仓**的计划数量。从所有 `pending` 状态的 ASN 明细聚合计算，不代表实物 |
| `received_stock` | 包裹已到仓签收、**尚未分拣**的计划数量。注意：签收时按 ASN 计划量记账，实物数量以分拣为准 |
| `sorted_stock` | 分拣完成、**尚未上架**的实物数量（含其中的破损品 `sorted_damage_stock`）。此阶段货物已清点，数量准确 |
| `sorted_damage_stock` | `sorted_stock` 里的**破损品**（待上架·破损），只能上到 damaged 库位。不变式 `0 ≤ sorted_damage_stock ≤ sorted_stock`；良品部分 = `sorted_stock − sorted_damage_stock`，只有这部分能上到 standard / return 库位 |

### 3. 出库流程过渡类（DN）

这四个字段随 DN 出库流程流转，货物完成客户签收后归零。

| 字段 | 含义 |
|------|------|
| `dn_stock` | 已创建 DN 单、**尚未开始拣货**的预扣数量。从所有 `pending` 状态的 DN 明细聚合计算。货物实物未动，仅做逻辑占位 |
| `picked_stock` | 已从货架拣出、**尚未打包**的实物数量 |
| `packed_stock` | 已打包完成、**尚未发货**的实物数量 |
| `delivered_stock` | 已交给承运商、**客户尚未签收**的在途数量。货物一旦发出即不再计入仓库总库存（有意设计） |

### 4. 汇总与阈值

| 字段 | 含义 |
|------|------|
| `total_stock` | 仓库内所有形态实物的合计（见下方公式），由程序在每次流程节点推进后重新计算 |
| `locked_stock` | `onhand_stock` 中被**手动冻结**的数量，当前预留给将来的手动冻结功能，业务流程中暂不使用 |
| `low_stock_threshold` | 补货告警阈值，`-1` 表示禁用 |
| `high_stock_threshold` | 积压告警阈值，`-1` 表示禁用 |

## 二、计算公式

### total_stock（仓库总库存）

```
total_stock = onhand_stock    ← 标准货位
            + damage_stock    ← 残次品货位
            + return_stock    ← 退货货位
            + sorted_stock    ← 分拣区，等待上架
            + picked_stock    ← 拣货区，已离架
            + packed_stock    ← 打包区，等待发货
```

不含 `asn_stock`（货在供应商处）、`received_stock`（极短暂中间态）、`dn_stock`（软预留，不额外计数）、`delivered_stock`（已出仓）。
`sorted_damage_stock` 是 `sorted_stock` 的一部分，不另外计入。

### available_stock（可出库量）

```
available_stock = onhand_stock + damage_stock + return_stock
                - locked_stock - dn_stock
```

包含残次品和退货品（历史口径，接口字段不变）。注意：拣货只能从 standard 库位拣（16162），这两类货物不能直接拣货出库，
要出库先移库到 standard 库位；判断能不能发货请看 `available_stock_for_sale`。减去 `locked_stock`（手动冻结）和 `dn_stock`（已被 DN 单占用）。

### available_stock_for_sale（纯净可售量）

```
available_stock_for_sale = onhand_stock - locked_stock - dn_stock
```

只计算标准货位的库存，适用于仅面向正常商品的销售场景。

> **注意**：`locked_stock` 当前始终为 0（手动冻结功能尚未上线），因此目前两个可用量的差值就是 `damage_stock + return_stock`。

## 三、库存页面字段对照

| 页面显示 | 对应字段 | 说明 |
|---------|---------|------|
| 总库存 | `total_stock` | 仓内所有形态实物合计 |
| 可用库存 | `available_stock` | 含残次/退货，减去预留 |
| 可售库存 | `available_stock_for_sale` | 仅标准在库，减去预留 |
| 在途入库 | `asn_stock` | 供应商已出单但未到仓 |
| 残次品 | `damage_stock` | 残次货位实物量 |
| 待上架 / 其中破损 | `sorted_stock` / `sorted_damage_stock` | 待上架合计 / 只能上破损库位的部分；列表另有 `pending_since`（见第八节） |
| 退货库存 | `return_stock` | 退货货位实物量 |
| 锁定库存 | `locked_stock` | 手动冻结量（当前为 0） |

## 四、ASN 入库流程——数值变化全链路

```
阶段            操作                        数值变化
─────────────────────────────────────────────────────────────────────
创建 ASN        pending ASN 明细写入        asn_stock  += 计划量
                                            （从 ASN 表重新聚合）

包裹签收         receive_asn                 asn_stock      -= 计划量
                                            received_stock += 计划量
                注意：此处按计划量记账，
                非实物清点数量

分拣完成         complete_asn                received_stock -= 计划量
（sorting task   （由分拣任务完成时           sorted_stock   += 实际分拣量（良品 + 破损）
 complete 触发） 自动触发）                  sorted_damage_stock += 破损量（damage_quantity）
                                            total_stock 重新计算

                实际分拣量 ≠ 计划量时：
                  少于计划 → sorted_stock 小于预期，差额核销
                  多于计划 → sorted_stock 超出计划，超出量正常入库

上架完成         putaway_completed           sorted_stock -= 上架量
                                            上到 damaged 库位：sorted_damage_stock -= min(上架量, sorted_damage_stock)
                                              （先扣破损，其余扣良品）
                                            上到 standard / return 库位：只能用良品部分
                                              （sorted_stock − sorted_damage_stock），超出 → 400 15016，
                                              details {good_pending, damaged_pending}
                                            GoodsLocation.quantity += 上架量
                                            触发 update_and_calculate_stock：
                                              onhand_stock = GoodsLocation(standard) 汇总
                                              damage_stock = GoodsLocation(damaged)  汇总
                                              return_stock = GoodsLocation(return)   汇总
                                            total_stock 重新计算
─────────────────────────────────────────────────────────────────────
```

**流向示意：**

```
供应商       asn_stock    received_stock   sorted_stock   GoodsLocation
  ○─────────►[     ]──────────────►[     ]─────────►[     ]──────────►[onhand]
          创建ASN       签收时              分拣完成          上架完成
                      （计划量）          （实际量）
```

## 五、DN 出库流程——数值变化全链路

```
阶段            操作                        数值变化
─────────────────────────────────────────────────────────────────────
创建 DN         pending DN 明细写入         dn_stock += 计划量
                                            （从 DN 表重新聚合）

进行中          progress_dn                 无库存变化，仅状态流转

拣货完成         picking_dn                  只能从 standard 库位拣：批次提交 / 改量 / 完成复核时库位类型
                                              不是 standard → 400 16162（details {location_id, location_type}）
                                            dn_stock      -= 实际拣货量
                                            picked_stock  += 实际拣货量
                                            GoodsLocation.quantity -= 实际拣货量
                                            触发 update_and_calculate_stock
                                            total_stock 重新计算

                缺货拣不满时：
                  dn_stock 按实际拣货量扣减，
                  剩余未拣量继续保留在 dn_stock 中

打包完成         packing_dn                  picked_stock  -= 已拣量
                                            packed_stock  += 打包量
                                            sorted_stock  += 已拣量 − 打包量
                                            total_stock 重新计算（不变）

                少打包时（按商品逐个结算）：
                  未打包的差额退回 sorted_stock（待上架，按良品：sorted_damage_stock 不变），
                  之后走上架放回库位；DN 按实际打包量发货。
                  整个打包任务一件没打包时不能完成（16082）

发货完成         delivery_dn                 packed_stock    -= 发货量
                                            delivered_stock += 发货量
                                            total_stock 重新计算

客户签收         complete_dn                 delivered_stock -= 签收量
                                            total_stock 重新计算

关闭 DN          close_dn                    dn_stock 重新聚合计算
（pending 状态）                             （DN 移出 pending 后自动减少）

取消 DN          dn_cancelled_after_picking  picked：picked_stock -= 已拣量，sorted_stock += 已拣量
（picked /                                   packed：packed_stock -= 已打包量，sorted_stock += 已打包量
 packed，未发货）                             （少打包的差额在打包完成时已退回 sorted_stock）
                                            total_stock 不变；退回的货按良品（sorted_damage_stock 不变），之后走上架放回库位
                                            DN 改为 closed，dn_stock 重新聚合（picked / packed 本就不预占）
                有未结束的承运商自动运单时不能取消（16110）；delivered / completed 不能取消（16052）
─────────────────────────────────────────────────────────────────────
```

**流向示意：**

```
GoodsLocation  dn_stock(预扣)  picked_stock  packed_stock  delivered_stock  客户
[onhand]──────►[          ]──►[          ]─►[          ]─►[            ]──► ✓
           创建DN        拣货完成       打包完成       发货完成         签收完成
```

## 六、其他操作对库存的影响

| 操作 | 影响字段 | 说明 |
|------|---------|------|
| **库存调整（Adjustment）** | `onhand_stock` / `damage_stock` / `return_stock` / `total_stock` | 直接修改 GoodsLocation（按差值累加；正向调整的库位还没有记录时新建，负向调整没有记录 → 16113），完成后触发 `update_and_calculate_stock` 同步到 Inventory。取消调整单（is_active=false）不动库存 |
| **循环盘点（CycleCount）** | 不直接改 Inventory | 盘点只记录系统数量和差异值，需另行发起库存调整才会真正改变库存。系统数在**录入实盘时**取当时的库位库存（不是开始盘点时的快照），盘点期间正常的出入库不会被算成差异；完成盘点前每条明细都必须已录入（16114） |
| **下架（Removal）** | `sorted_stock` ↑（破损品同时 `sorted_damage_stock` ↑），`onhand/damage/return` 同步更新 | GoodsLocation 减少 → 触发重算；货物进入 sorted_stock 等待重新上架或处置。从 damaged 库位下架、或下架原因是 damage / damaged 的按破损品记进 `sorted_damage_stock`（之后只能上到 damaged 库位）。对外接口的 reason 有白名单，`picking` 只由拣货完成内部使用（货走 picked_stock） |
| **库存快照（Snapshot）** | 无 | 只读，将当前 GoodsLocation.quantity 按时间切片存档（只有库位库存）。一期起历史库存以日终结存为准（第十节），旧快照照常每日拍、作核对用 |

## 七、关键设计说明

以下设计在阅读代码时容易产生疑问，特此说明。

**1. `damage_stock` 和 `return_stock` 计入可用量**

`available_stock` 包含这两个字段（历史口径，字段不变）。但破损品只能上到破损库位、拣货只能从 standard 库位拣（16162），
这两类货物不能直接发货；能发货的量看 `available_stock_for_sale`。

**2. `delivered_stock` 不计入 `total_stock`**

货物一旦交给承运商，即视为离开仓库，不再计入仓库总库存。`delivered_stock` 只用于追踪"在途但尚未被客户签收"的状态，与仓库库存计算无关。

**3. `received_stock` 使用计划量而非实物量**

包裹签收时（`receive_asn`）并不清点实物，直接按 ASN 计划量增加 `received_stock`。实物数量以分拣结果（`actual_quantity`）为准，最终体现在 `sorted_stock` 中。因此 `received_stock` 是一个计划量占位符，在分拣完成后会用相同的计划量抵消归零，计划量与实物量的差异完全由 `actual_quantity` 吸收。

**4. `locked_stock` 当前未启用**

`lock_inventory` / `unlock_inventory` 方法已就绪，预留给将来的手动冻结功能（例如质检扣押、纠纷冻结等场景）。目前 `locked_stock` 始终为 0，`available_stock_for_sale` 实际等于 `onhand_stock - dn_stock`。

**5. `dn_stock` 按实际拣货量扣减**

拣货完成时（`dn_picked`），`dn_stock` 按**实际拣货量**（`picked_quantity`）扣减，而非原始预扣量。缺货拣不满时，未拣部分继续保留在 `dn_stock` 中，直到 DN 关闭后随聚合计算自动清除。

**6. `asn_stock` 和 `dn_stock` 的更新机制**

这两个字段不是增量 +/-，而是在相关单据创建/关闭时**重新从订单表聚合计算**（分别查询 pending 状态的 ASN/DN 明细求和）。因此它们始终与订单表保持一致，不存在累积误差。

**7. 待上架·破损（`sorted_damage_stock`）**

设计意图是破损品上到破损库位：分拣完成时破损数量同时记进 `sorted_stock` 与 `sorted_damage_stock`；上架到 damaged 库位先扣破损，
上到 standard / return 库位只能用良品部分（超出 400 15016）。退回待上架的（少打包、DN 取消）都按良品；从破损库位下架或因破损下架的
按破损品。升级前已在待上架里的货全部按良品（迁移 `e7b4c2a9d1f3` 默认 0，存量里分不出哪些是破损的）。
注意移库（Transfer）、库存调整（Adjustment）不经过待上架。从破损 / 退货库位移回 standard 库位允许，但必须填原因（400 15018，原因写进库存流水的备注，第九节）。

## 八、待上架列表、汇总与停留时间

- 列表：`GET /warehouse/inventory/?pending_putaway=true`（也接受 `1`）只返回 `sorted_stock > 0` 的行，每行带 `sorted_stock`、
  `sorted_damage_stock`、`pending_since`（列表统一省略空值：没有时不出现）。库存详情同样带 `pending_since`。
- 汇总：`GET /warehouse/inventory/pending-putaway/summary`（权限 inventory_read / putaway_read / putaway_edit 任一）。范围同库存列表：
  `warehouse_id` 参数或 `X-WAREHOUSE-ID` → 该仓库，否则调用方可访问的仓库；`company_id` 再按公司收窄；`overdue_days`（默认 3，0–365）。
  返回 `{warehouse_id, company_id, inventory_count, goods_count, total_quantity, damaged_quantity, good_quantity, overdue_days,
  overdue_quantity, overdue_inventory_count, oldest_pending_since}`。
- `pending_since`（最早一件待上架的进入时刻，UTC、+00:00）：上架记录不记来自哪一笔入账，按**先进先上**估算——某商品在某仓库的入账
  从最近一笔往回累加，凑够当前 `sorted_stock` 为止，最早那一笔的时刻。入账来源与时刻：分拣完成（入库单完成时刻 `completed_at`，
  旧数据没有按创建时刻）、少打包退回（打包完成时刻 `DN.packed_at`）、DN 取消退回（取消时刻 `DN.closed_at`）、下架（拣货下架除外，
  `removal_time`）。入账合计不够当前待上架（旧数据、直接改过库存）时按最早一笔算；一笔都没有为空。
  超期件数同样按先进先上：截止时刻（现在 − `overdue_days` 天）之后的入账最多算 `sorted_stock` 件没超期，其余算超期；来历不明的部分算超期。
  逻辑在 `warehouse/inventory/pending.py`（常量 `PENDING_PUTAWAY_OVERDUE_DAYS = 3`）。

## 九、统一库存变动服务与库存流水（库存底座一期）

代码：`warehouse/stock/`（`service.py` StockService、`guard.py` 写入守卫、`audit.py` 对账、`models.py` 各表）。

### 1. 三张行表 + 一个缓存

| 表 | 粒度 | 放什么 |
|---|---|---|
| `goods_locations` | 商品 × 库位 × 批次 | 库位上的库存（类别按库位类型：standard → onhand、damaged → damaged、return → return）。唯一索引 `(goods_id, location_id, coalesce(lot_id, 0))`，数量为 0 删行 |
| `inventory_lot_stock` | 仓库 × 商品 × 批次 | 仓内、不在库位上的库存：`sorted_stock`（待上架合计）/ `sorted_damage_stock`（其中破损）/ `picked_stock` / `packed_stock` / `delivered_stock`（已发未签）。各列全为 0 删行 |
| `stock_ledger` | 每笔变动按桶一行 | 库存流水（只增不改） |
| `inventory`（缓存） | 商品 × 仓库 | `onhand / damage / return / sorted / sorted_damage / picked / packed / delivered / total` = 上面两张行表的合计，由 StockService 增量维护 |

一期批次（`lot_id`）一律为空：`goods_lots` 只建了表，二期启用。`asn_stock / received_stock / dn_stock / locked_stock` 是单据派生的数（不是实物），
仍由 InventoryService 按单据维护，不记流水。

### 2. StockService

所有改实物库存的地方都经过它（`StockOp(...).move(...).commit()`）：

| 入口 | 变动类型 | 来源桶 → 去向桶 | 单据（doc_type / doc_id / doc_line_id） |
|---|---|---|---|
| 分拣完成（入库单完成） | `sort_in` | （仓外）→ pending / pending_damaged | asn / ASN / ASN 明细 |
| 上架（单条、批量） | `putaway` | pending*（破损库位先扣破损，其余扣良品；standard / return 只能用良品，15016）→ 库位 | putaway / 上架记录 |
| 下架（单条、批量） | `removal` | 库位 → pending（破损库位、或原因 damage / damaged → pending_damaged） | removal / 下架记录，reason = 下架原因 |
| 拣货完成 | `pick` | 库位 → picked（一笔合成，原来的「拣货下架 + dn_picked」） | picking_task / 拣货任务 / 拣货明细；doc_no = DN 单号 |
| 打包完成 | `pack` / `pack_short_return` | picked → packed；少打包的差额 picked → pending | packing_task / 打包任务 / DN 明细 |
| DN 拣货后取消 | `dn_cancel_return` | picked 或 packed → pending | dn / DN / DN 明细 |
| 发货 | `ship` | packed → in_transit；`occurred_at` = 实际发货时刻（`shipped_at`） | dn / DN / DN 明细 |
| 签收（含承运商跟踪、自动视为签收） | `sign` | in_transit →（仓外）；`occurred_at` = 签收时刻 | dn / DN / DN 明细 |
| 移库（单条、批量） | `transfer` | 库位 → 库位 | transfer / 移库记录 |
| 调整单完成 | `adjust_gain` / `adjust_loss` | （仓外）→ 库位 / 库位 →（仓外） | adjustment / 调整单 / 调整明细，reason = 调整原因 |
| 期初 / 系统校正 | `opening` / `reconcile` | （仓外）↔ 各桶 | — |

- 加锁顺序（B-103 的扩展，`common/locks.py`）：Inventory(goods, warehouse) → GoodsLocation(goods, location, lot) → InventoryLotStock(goods, lot)，
  各自按键升序一次锁齐；后两张表只在持有同一商品 Inventory 行锁时才写，不会引入新的死锁顺序。不存在的行在 savepoint 里新建（B-107）。
- 来源不足沿用原错误码：库位 15001（调整单 15002）、待上架 15007 / 15016、已拣 15009、已打包 15010、已发 15011。
- 进货的库位必须启用（16085；期初、校正除外）。InventoryService 只保留单据派生数（asn / received / dn）、阈值与查询。
- 移库：**从破损 / 退货库位移回 standard 库位必须填原因**（`reason`，没给时非空的 `remark` 也算）→ 否则 400 `15018`；原因写进流水备注，
  `remark` 为空时也记进移库记录的 `remark`。其它方向不要求。

### 3. 流水的字段

`posted_at`（记账时刻，日终库存按它算）、`occurred_at`（业务发生时刻，列表默认按它）、`company_id`、`warehouse_id`、`goods_id`、`lot_id`、
`location_id`（只有库位类别有）、`stock_type`（onhand / damaged / return / pending / pending_damaged / picked / packed / in_transit）、
`quantity`（带符号）、`balance_after`（本行之后同一桶的结存，按 `(posted_at, id)` 衔接）、`goods_total_after`（本笔之后该商品在该仓库的
`total_stock`，不含在途）、`counter_stock_type`（同一笔变动另一侧的类别，空 = 仓外；进销存据此判断是不是仓内搬动）、`movement_type`、
`doc_type / doc_id / doc_no / doc_line_id`、`reason`、`operator_id`（请求的当前用户；定时任务 / 承运商回调为空）、`api_key_id`、
`source`（API Key → api；没有请求上下文 → system；请求头 `X-Client-App: pda/<版本>` → pda；其余 web）、`trace_id`（同一事务的所有行共用；
请求头带合法的 `X-Request-ID`（`[A-Za-z0-9-]{8,64}`）时直接用它）、`remark`。

### 4. 接口（权限 inventory_read；范围同库存列表）

- `GET /warehouse/stock-ledger/`：列表。筛选 `warehouse_id`（或 X-WAREHOUSE-ID）、`company_id`、`goods_id`、`goods_code`、`keyword`、`lot_id`、`lot_no`、
  `location_id`、`location_code`、`stock_types`、`movement_types`、`doc_type`、`doc_id`、`doc_no`、`doc_line_id`、`operator_id`、`source`、
  `trace_id`、`start_time` / `end_time`（只给日期 = 仓库当地那一天）、`time_field=occurred|posted`、`order=desc|asc`，分页同其它列表。
- `GET /warehouse/stock-ledger/summary`：进销存（期初 / 入 / 出 / 期末，按记账时刻）。`stock_types` 为统计边界（默认仓内实物 = total_stock 口径），

## 十、期初、历史库存与历史回放

### 1. 期初与部署

- `flask stock init-ledger`：流水为空时才执行（幂等）。无批次的 `inventory_lot_stock` ← inventory 计数器；缓存 ← 行表；把当前结存写成 `opening` 行；
  再把旧快照转成流水覆盖之前各天的日终结存（`legacy_snapshot`，只有库位库存）。
- 部署流水线（`.github/workflows/deploy.yml`）：迁移 → 权限种子 → `init-ledger` → 重启 → 健康探测 → `flask stock reconcile --apply`
  （部署前的版本没有 StockService 时加 `--sync-legacy-counters`）。迁移跑完到重启之间旧进程还在接请求，它们改了库存不写流水、
  也不改 `inventory_lot_stock`；校正把「当前结存 − 流水合计」写成 `reconcile` 行并打印出来。上线选仓库不作业的时段。
- 迁移 `5b8e2d7c4a91` 只做 DDL 和一条 `INSERT … SELECT`（按 inventory 计数器回填无批次的 `inventory_lot_stock`），期初流水不放在迁移里。

### 2. 日终结存 `stock_daily_balances`

- 口径：仓库当地日期 D 的 24:00 = D 结束（当地次日 00:00）之前**记账**的流水合计。已过去的日子查出来不会再变；补录的发货时刻早于记账时刻时，
  算在记账那一天（实际发货时刻以流水明细为准）。
- 生成：调度器每小时（`STOCK_DAILY_MINUTE`，默认第 7 分钟）检查，对「当地已过 0 点、前一天还没生成」的仓库补生成（缺几天补几天，增量：前一天 + 当天流水）。
  `flask stock daily` 同；`flask stock rebuild-daily --from --to` 重建。旧快照（`inventory_snapshot`）一期照常每天拍，作为独立的核对口径，历史库存的查询以日终结存为准。
- 查询：D ≥ 当地今天 → 实时；已生成 → 查表；流水覆盖内还没生成 → 现算；更早 → 旧快照转换的行（`coverage = on_shelf_only`）。回放之后从回放起点（线上 2025-09-21）可查。

接口（权限 inventory_read；要指定一个仓库，调用方只能访问一个仓库时自动用它）：

- `GET /warehouse/inventory/history?date=&goods_id=&keyword=&location_id=&stock_types=&group_by=goods|goods_location|location|goods_lot`
  → `{date, warehouse_id, coverage: full|on_shelf_only|none, source: realtime|ledger|derived|computed|legacy_snapshot|none, history_start,
  group_by, total, page, per_page, items: [{goods | location, onhand, damaged, return, pending, pending_damaged, picked, packed, in_transit, total}]}`
- `GET /warehouse/inventory/history/export`（CSV）、`/history/at?time=`（任意时刻）、`/history/series?from=&to=&goods_id=|goods_ids=`（每天日终合计，
  多商品迷你走势线，最多 100 个商品、400 天）、`/history/flows?from=&to=&goods_id=&keyword=`（每日入库 / 出库量）。

### 3. 历史回放 `flask stock replay`（`warehouse/stock/replay.py`）

从现有单据回放期初（`opening` 的时刻 T0）之前的流水，逐批和旧快照核对：入库单完成 → sort_in；上架 / 下架（拣货下架记 pick）/ 移库记录；
调整单完成；DN 打包（含少打包退回）、发货、签收、拣货后取消。待上架一律按良品回放（升级前的系统不分破损）；来源不够也照记（报告里给出次数）；
已经在流水里的单据不再回放。

- 默认**演练**：只输出报告（事件数、各变动类型的数量、负结存次数、逐批快照的不一致行数与最大差额及样例、回放到 T0 的结存与期初的差额）。
  `--report <文件>` 输出完整 JSON。不写库，也可以在部署前对生产库只读运行（表不存在时与当前库存比）。
- `--apply`（要求已有 opening 行、还没有回放过）：写回放出的流水（`source = system`、`trace_id = replay-…`、`posted_at = occurred_at`）；在 T0 把
  「期初 − 回放到 T0 的结存」写成 `reconcile` 行并删掉 `opening` 行——T0 的结存不变，之后的真实流水不受影响；用回放的流水重建 T0 之前各天的
  日终结存（`derived`，取代 `legacy_snapshot`）。差异太大就不 apply，保留「T0 期初 + 旧快照（只有库位库存）」。

### 4. 历史数据校正 `flask stock fix-legacy-pending`（`warehouse/stock/legacy_fixes.py`）

已确认的旧 bug 造成的计数差额（回放演练发现，2026-10-25 生产核对）：

- **B-06**（58c6a68，2026-09-29 03:50:30 UTC 之前）：拣货下架（`removal_records.reason = 'picking'`）走了普通下架，货同时进了待上架和已拣，
  待上架计数里多出拣货下架的数量（实物不在待上架区）。生产 Kyoto#1：有待上架计数的 1,095 个商品「计数器 − 单据推算的待上架」都正好等于
  修复前的拣货下架量，合计 5,274 件。
  单据推算的待上架 = 入库单完成的实收 + 非拣货下架 + B-54 修复后的少打包退回 + 拣货后取消退回 + 本命令 B-54 校正退回的量 − 上架记录。
  校正：待上架（良品）→（仓外），数量 = min(修复前拣货下架量, 计数器 − 单据推算, 待上架良品)：不扣到负数，不动破损部分。
- **B-54**（2f8327e，2026-10-04 15:18 UTC 之前）：少打包时差额留在已拣，此后不会再结算。生产：3 张已发货的 DN（2025-09-23、2026-06-22、
  2026-07-04 打包）留下 10 个商品共 32 件。`--include-picked` 时按现行规则退回待上架（已拣 → 待上架良品），之后由仓库上架放回，找不到的走调整单报损；
  数量 = min(修复前少打包差额, 已拣计数器 − 拣货完成、打包未完成的 DN 的已拣量)。

用法：`flask stock fix-legacy-pending [--warehouse N] [--include-picked] [--report 文件] [--limit 30]` 只出报告（每个商品：当前待上架（其中破损）、
单据推算及其构成、修复前拣货误计量、差额、拟扣减量；B-54：已拣、进行中的 DN 已拣量、修复前少打包差额、拟退回量；合计）；加 `--apply` 才写。
写入时逐个商品在其 Inventory 行锁下重算后经 StockService 记账：`movement_type = correction`，`reason = B-06 / B-54`，`doc_type = legacy_fix`，
`doc_no` = bug 编号，备注写明原因与依据，`trace_id = fix-<bug>-<时刻>`；已有同一 bug 校正流水的商品跳过（重复运行不会重复扣）。

与历史回放的先后：互不影响结果。回放 `--apply` 只替换期初时刻 T0 的 opening 行（T0 结存不变、差额在 T0 写 reconcile）并重建 T0 之前的日终；
校正是 T0 之后的一笔新流水，两边都不读对方写的行。建议先校正（它影响当前的待上架列表和上架作业，不必等回放的决定），再看回放演练报告决定是否 apply：
回放对 T0 的差额仍然是这两个 bug 的量（5,274 件待上架、32 件已拣），已有校正流水解释，T0 之前的日终按单据重建为真实值，T0 到校正之间的日终如实反映当时系统里的数。
